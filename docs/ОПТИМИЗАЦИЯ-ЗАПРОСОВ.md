# Минимизация обращений к Firestore

Документ-план: как устроены запросы сейчас и что можно урезать. Ориентир — чтения документов (они тарифицируются поштучно). Записей у нас на порядки меньше чтений, поэтому экономия идёт именно по чтениям.

Обозначения: **N** — число комментариев номера, **U** — число авторов на странице, **P** — размер страницы (сейчас 5).

---

## 1. Комментарии (страница номера)

### Как сейчас

| Режим | Запрос | Чтений |
|---|---|---|
| Сначала новые / старые | `numberId + status + createdAt`, `limit 5`, догрузка через `startAfter` | 5 за страницу, +5 за «Показать ещё» |
| **Популярные** | `numberId + status`, **без limit и без orderBy** — грузит ВСЕ комментарии номера, сортировка на клиенте | **N за один клик** |
| Fallback без индекса | весь номер целиком | N |

Кэш: `comments:` ключ с учётом сортировки нет! Ключ `comments:{nid}[:uid]` один на все три режима — при переключении «старые → новые» показывается устаревший порядок из кэша до истечения TTL (это и баг, и скрытая экономия: повторный клик по сортировке бесплатен). TTL 10 мин, для номеров старше 7 дней — 1 час.

### Проблема

«Популярные» — единственный режим, читающий N документов. На обсуждаемом номере со 100+ комментариями это 100 чтений за один клик, у каждого посетителя.

### План

1. **Индекс для топа**: `comments`: `numberId↑, status↑, likeCount↓, createdAt↑` → запрос `orderBy likeCount desc, createdAt asc, limit 5, startAfter`. Стоимость топа падает с N до 5 за страницу, как у остальных режимов. Плюс: likeCount уже поддерживается правилами (меняется ровно на ±1 вместе с лайком).
   - Риск: «популярные» при пагинации нестабильны — лайки меняют порядок между догрузками. Принимаемо: сортировка топа и так «плавает» по природе.
   - Без индекса код уже умеет откатываться на «грузить всё» — поведение не сломается.
2. **Разделить ключ кэша по режиму**: `comments:{nid}:{mode}[:uid]`. Параллельно лечит баг с устаревшим порядком при переключении.
3. **Кэшировать «Показать ещё» вместе со страницей** — уже делается (`cput` после догрузки), оставить.
4. TTL не трогать: 10 мин/1 ч — разумный баланс. Можно поднять `commentsOld` до 4–6 часов для номеров прошлых лет: комментарии там меняются раз в месяц. Экономия мелкая, но бесплатная.

**Итог по комментариям:** типичный сеанс «открыл номер, полистал, переключил сортировки» сейчас ~15–20 + N чтений, станет ~15–20 чтений.

## 2. Лайки

### Как сейчас

- Мои лайки на номер: 1 запрос (`likes` по `uid + numberId`), кэш 10 мин — **это норма, не трогаем**.
- Число лайков на комментарии приходит полем `likeCount` в самом комментарии — **бесплатно, так и задумано**.
- Список лайкнувших: 1 запрос с `limit 200`, только при раскрытии, кэш 30 сек.
- Переключение лайка: чтение `usage/{uid}_d*` перед записью (1 чтение на лайк).

### План

1. **Список лайкнувших: limit 200 → 50.** Больше 50 лайков под одним комментарием у нас не бывает; лишний потолок — мёртвая зона чтений, когда комментарий реально наберёт много.
2. **Чтение usage перед лайком — кэшировать на сессию.** Сейчас каждый лайк = 1 лишнее чтение. Лимит можно проверять по локальному счётчику сессии (правила всё равно подстрахуют на уровне базы), usage читать один раз при входе на страницу. Экономия: 1 чтение × число лайков за сеанс.
3. TTL списка лайкнувших 30 сек → 5 мин. Повторное раскрытие того же комментария почти всегда показывает то же самое.

## 3. Оценки

### Как сейчас (уже хорошо)

- Сводка номера: **1 чтение** `rateAgg/{nid}` вместо всех оценок — главная оптимизация уже сделана.
- Оценки авторов комментариев: пакетами по 30 через `documentId in` — минимально возможное.
- Моя оценка — в том же пакете.

### План

1. **Добить fallback**: пока у номера нет `rateAgg` (ни разу не пересчитывался и не было оценок), читается `ratings` целиком (до 500). После того как `rateAgg` появится у всех номеров с оценками, ветку «грузить всё» можно оставить, но она перестанет срабатывать. Действие: один раз нажать «Пересчитать» (админ) — это уже запланировано отдельно.
2. **`loadUserRatings` (limit 300) — мёртвая ветка**: рядом лежит пагинированная `loadUserRatingsFirst/More` (по 5). Проверить, что старая функция нигде не вызывается, и удалить — на странице человека оценки уже грузятся по 5.
3. Чтение usage перед выставлением оценки — та же оптимизация, что у лайков (кэш на сессию).

## 4. Аватары и имена

### Как сейчас (уже хорошо)

- Пакетами по 30 uid за запрос, кэш 14 дней (`TTL.avatar`) — практически оптимум.
- Повторные страницы того же посетителя почти бесплатны.

### План

Не трогаем. Опционально: при показе лайкнувших и комментариев сначала рендерить без аватаров и догружать — уже так и есть.

---

## 5. Самое обсуждаемое (buzz / hot)

### Как сейчас

- Полоса на главной: `buzz` с `orderBy total desc, limit 5` → **5 чтений, только при раскрытии блока**. Отлично.
- Страница /hot/: два запроса (неделя + всё время) с limit.
- Кэш 10 мин, ключ включает номер недели.

### План

Не трогаем. Это эталонный блок: агрегат вместо сырых данных, lazy-load, кэш.

---

## 6. Страница человека и кабинет

### Как сейчас

- Комментарии человека: по 5 с `startAfter` — ок.
- Оценки: по 5 (после чистки мёртвой ветки из п.3.2) — ок.
- Плейлисты: `limit 60` — ок.
- Заявки: на странице человека 1 чтение `claims/{pid}`; в кабинете `claims` по uid.
- Проверка админа: 1 чтение `admins/{uid}`, кэш 3 суток — ок.

### План

1. `loadUserRatings` 300-limit — удалить (см. п.3.2).
2. Остальное не трогаем: всё уже пагинировано или одиночными чтениями.

## 7. Записи: что неизбежно

Записи дешевле чтений, но пакеты (batch) у нас и так сгруппированы: лайк = лайк + счётчик + usage одним батчем; комментарий + usage + buzz одним батчем; оценка + rateAgg одним батчем. Улучшать нечего — это уже оптимум.

Правила делают служебные чтения при записи (`existsAfter`, `getAfter`) — это цена безопасности лимитов, убрать нельзя без переноса логики на сервер, что для нашего масштаба не нужно.

---

## 8. Админский пересчёт

### Как сейчас

Читает **все** комментарии, **все** оценки, весь `buzz`, весь `rateAgg` — сотни-тысячи чтений за нажатие. Для админа, раз в неделю — терпимо, но это самая дорогая операция системы.

### План (низкий приоритет)

- Запускать реже: кнопка уже показывает дату прошлого пересчёта — добавить мягкое предупреждение «прошло меньше суток, точно надо?».
- Полный перенос на Cloud Functions (серверный инкремент при создании комментария/оценки) — **не делаем**: текущая схема «клиентские инкременты + ручной пересчёт» проще и без бэкенда; нагрузка на пересчёт исчезает сама, когда клиентские инкременты стабильны.

## 10. Итоговая таблица «до → после»

Типичный сеанс на странице номера с 100 комментариями:

| Действие | Сейчас | После |
|---|---|---|
| Открыть номер (первые 5) | ~10 | ~10 |
| «Показать ещё» ×2 | 10 | 10 |
| Переключить в «Популярные» | 100+ | 5 |
| Досмотреть топ до конца | 0 (уже всё загружено) | 5×страницы |
| Поставить 3 лайка | 3 (usage) | 0 (кэш сессии) |
| Раскрыть 2 списка лайков | 2 запроса ≤200 | 2 запроса ≤50 |
| **Итого** | **~125+N/…** | **~30** |

Порядок работ: (1) индекс + пагинация топа + ключ кэша, (2) limit лайкнувших, (3) кэш usage на сессию, (4) удаление мёртвой ветки оценок, (5) TTL для старых номеров. Каждый пункт независим и откатываем.
